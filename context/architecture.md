# Architecture Context

## Stack

| Layer           | Technology                         | Role                                                                 |
| --------------- | ---------------------------------- | -------------------------------------------------------------------- |
| Frontend        | React + TypeScript (Vite)          | Onboarding, daily recommendation view, history and savings dashboard |
| Charts          | Recharts                           | Rainfall, demand, and estimated-savings visualizations               |
| Backend         | Python + FastAPI                   | REST API, orchestration, recommendation engine                       |
| Validation      | Pydantic                           | Request/response schemas and input validation                        |
| Database        | SQLite (via SQLAlchemy)            | Property profiles, recommendations, user-reported actions            |
| Weather data    | Open-Meteo (forecast + historical) | Rainfall, temperature, wind, reference evapotranspiration (ET₀)      |
| Testing         | pytest (backend), `npm run build` (frontend) | Calculation correctness and build verification            |
| Hosting         | Free-tier static host (frontend) + free-tier Python host (backend) | Public demo deployment                |

Open-Meteo's free API is for non-commercial use. This is
acceptable for the hackathon; any commercial deployment
needs a different data arrangement.

## System Boundaries

- `frontend/` — All UI. Renders data returned by the
  backend. Owns no irrigation logic and never calls
  Open-Meteo directly.
- `backend/app/api/` — HTTP routes and request/response
  schemas. Thin: validates input, calls services, returns
  results. Contains no calculation logic.
- `backend/app/engine/` — Pure recommendation and
  water-balance calculation. Takes plain inputs (weather
  values, property settings) and returns a recommendation
  plus its reasoning. No network, no database, no
  framework imports.
- `backend/app/services/` — External integrations,
  starting with the Open-Meteo client. Also holds the
  recommendation orchestration service: it loads weather,
  maps it to engine inputs, calls the pure engine, and
  stores the result. Routes stay thin.
- `backend/app/db/` — SQLAlchemy models, session handling,
  and queries. The only place that touches the database.
- `context/` — Spec files (workflow rules, architecture,
  progress tracker, and the other context files). Source
  of truth for what to build.

## Storage Model

- **Database (SQLite, via SQLAlchemy)**: the profiles table is
  implemented in `backend/app/db/models.py`. All columns are
  required:
  - `id` — UUID4 string, primary key, generated by the server
  - `location_label`, `latitude`, `longitude`
  - `lawn_area_m2`
  - `grass_type`, `soil_type`, `sprinkler_type` (stored as
    names; the supported preset values are not finalized)
  - `precipitation_rate_mm_per_hour`
  - `baseline_minutes_per_event`, `events_per_week`
  - `last_watered_date`, `last_watered_minutes`
- The database URL comes from `DATABASE_URL` (default
  `sqlite:///./lawn_advisor.db`). Tables are created on
  application startup; there is no migration tool in the MVP.
- The recommendations table is implemented in
  `backend/app/db/models.py`. Each row stores:
  - `id` — UUID4 string, primary key
  - `profile_id` — the profile the recommendation belongs to
  - `created_at`
  - `state` (SKIP, REDUCE, or WATER), `recommended_depth_mm`,
    `reason`, and `uncertainty`
  - the Why numbers: `taw_mm`, `raw_mm`,
    `skip_threshold_mm`, `horizon_days`,
    `projected_depletions_mm`, and
    `projected_max_depletion_mm`
  - `baseline_event_mm` and `irrigation_efficiency`
  - `config` — the full `EngineConfig` snapshot
  - `forecast_inputs`, `observed_inputs`, and
    `profile_inputs` — the weather and property values used
  - `assumptions` — the assumption and source texts shown to
    the user
- The recommendation response also returns observed
  rainfall, forecast rainfall, forecast ET0, and estimated
  crop demand for the Why section. These are computed from
  the stored inputs and config, so the row keeps the
  explanation reproducible.
- The recommendation route is
  `GET /profiles/{profile_id}/recommendation`. Orchestration
  lives in `backend/app/services/recommendation.py`; the
  route only loads the profile, calls the service, and
  returns the result.
- Scientific constants are supplied to the orchestration
  service by a resolver. The verified constants table is
  still pending (Unit 6); until it is supplied, the resolver
  returns `None` and the route returns the
  "cannot recommend" state with code
  `constants_unavailable`. No scientific value is invented
  in code.
- **Still to add**: user-reported actions (followed or not).
  Profiles and recommendations are the tables so far.
- **Not stored**: Raw weather payloads beyond what a
  recommendation needs for explanation. Weather is
  re-fetchable from Open-Meteo; small cached daily values
  may be kept to reduce API calls and keep the demo
  working if the API is slow.
- No file or blob storage is needed for the MVP.

## Auth and Access Model

- No user accounts in the MVP. A property profile is
  created during onboarding and identified by a random ID
  held in the browser. This keeps the demo friction-free
  and avoids building auth during a two-week build.
- Every profile is independent. There is no sharing and no
  multi-property or multi-user access in the MVP.
- Profiles hold no sensitive personal data. Location is
  stored only at the precision needed for weather lookup
  (approximate coordinates or city).
- The backend validates that a request only reads or
  mutates the profile whose ID it presents. The path
  parameter is the only profile identifier accepted:
  creation cannot supply an ID, and an update cannot change
  it.

## Invariants

1. The application never controls sprinklers or any
   hardware. It only produces recommendations; the
   homeowner decides and acts.
2. All irrigation calculation lives in `backend/app/engine/`
   as pure functions with unit tests. Routes, services,
   and the frontend never duplicate or modify that logic.
3. Every recommendation is stored with the inputs,
   constants, and assumptions that produced it, so the UI
   can always explain why.
4. Every water-savings number is labeled as an estimate and
   computed against an explicitly defined baseline
   schedule. The product never presents estimates as
   measured savings.
5. Constants (crop coefficients, efficiencies,
   precipitation rates) come from cited sources or are
   explicitly marked as assumptions in the calculation
   spec. None are invented in code.
6. The frontend talks only to the backend API. Weather
   provider calls happen only in `backend/app/services/`,
   so the provider can be swapped without touching the UI
   or engine.
7. If weather data is unavailable, the system returns a
   clear "cannot recommend" state with a reason. It never
   guesses a recommendation.
8. Request handlers do not run long-lived background work.
   The MVP computes recommendations on request.
